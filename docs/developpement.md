# Développer Le Bureau

## Dossiers

| Dossier | Contenu |
| --- | --- |
| `page/office_template.html` | Squelette : en-tête, canvas, barre de lecture, panneau, les 4 blocs `kronn-action` (Kronn les lit dans le HTML statique), marqueurs `/*__STYLES__*/` et `/*__SCRIPTS__*/` |
| `page/src/styles.css` | Toute la feuille de style |
| `page/src/NN-*.js` | Le script, concaténé **dans l'ordre des noms** en un seul `<script>` (une portée globale, pas de modules) : config `00`, plan `10`, sprites `20`, données `30-33`, états `35`, dessin `40-45`, panneau, actions, fiches et éditeur `50-65`, récap `69`, tuiles, fil et « Qui fait quoi » `70-72`, mode TV `75-76`, souris `80`, boucle et démarrage `90` |
| `workflows/` | Scripts Python des étapes Exec ; `_lib.py` = socle commun et `_plan.py` = règles des plans (aussi utilisées par `tools/plan.py`), recopiés dans chaque script qui les importe au rendu (Kronn lance `python3 -c` sans fichier voisin) ; `templates/` = modèles des workflows et du Quick Prompt |
| `layouts/` | Plans de bureau (format `bureau-layout/1`) ; `open-space.json` = le plan type (équipe neuve), `equipe.json` = celui de l'équipe equipe, `exemple-startup.json` = un autre bureau (30 x 16, sans plateau TV) |
| `team/` | `defaults.json` : valeurs communes proposées à l'installation (Kronn, rythme, Jira et GitHub vides) |
| `teams/<équipe>/` | Profil d'équipe : `team.json` (nom, organisation GitHub requise, plan), `roster.json` (l'équipe), `defaults.json` (Jira, GitHub, titre), `music/` (morceaux des collègues), `cast.json` (recettes de leurs avatars), `sprites/` et `sprites.json` (sprites fournis et leurs planches, `sprites/build_sprites.py`). `teams/equipe/` = l'équipe de Rémi, réservée aux membres d'acme |
| `sprites/` | Recettes d'avatars communes `cast.json` (agents, intérimaires, visiteurs, équipe de démo), calques LPC `layers.json` ; `custom/` et `sprites.json` = sprites fournis d'une installation, jamais commités |
| `data/` | Instantanés de démo, équipe fictive Dunder Mifflin (aperçu local, captures et tests seulement, jamais dans la page publiée) |
| `tools/` | `install.py`, `uninstall.py`, `publish.py`, `templates.py`, `assemble.py`, `smoke.py`, `test.sh`, `shots.py` |
| `tests/` | `node --test` (sans npm) et `unittest` : logique de la page, états, installateur, modèles, scripts contre un faux Kronn et un faux `gh` |

## Configuration

- `bureau.config.json` : **propre à chaque installation**, jamais commité. Toutes les valeurs de l'installation : `kronn` (API, interface, projet), `page_id`, `workflows` (crons), `actions` (boutons), `own` (workflows gardés tels quels), `jira`, `github`, `rhythm` (fuseau, daily, heures de bureau, gel des MEP), `mep_workflow`, `agents`, `boss_pages` (pages Kronn de l'écran du boss, demandées à l'installation), `launch` (tes workflows lancés depuis la fiche d'un ticket : un id, ou `{wf, vars}` pour renommer ou retirer les variables, `LAUNCH_VARS` et `action_block()` dans `assemble.py` ; par défaut `impl` reçoit `jira_ticket_key`, `mep` `jira_ticket_key` et `pr_number`, `review` `repo` et `pr`, `fix` `pr` et `notes` ; Kronn relit ces valeurs dans le dataset `actions`, publié en JSON plat par le cron équipe, étape `actions`, parce qu'il ne lit pas le dataset `team` stocké en texte), `gitfut` et `wiki_posters` (facultatifs : par défaut déduits du roster, logins `github` et `passion.top3.wiki`, injectés ainsi dans les scripts par `templates.script_code`), `chrome` (chemin du navigateur des miniatures, `false` pour les désactiver).
- `owner` = clé de qui a installé la page : cette personne prend le bureau du boss. `team` = le profil d'équipe (absent : équipe neuve). `people` = les personnes ajoutées à cette installation (jamais dans le roster partagé), `music` = leurs morceaux. Relancer l'installateur garde les clés qu'il ne gère pas (posées à la main). `layout` = le plan du bureau (défaut : celui du profil, sinon `layouts/open-space.json`).
- Le roster vu par la page et les scripts = celui du profil, puis `people` (`roster()` dans `assemble.py`, seul point d'accès, comme `defaults()` et `music()`).
- Mises en prod suivies : `github.repo` avec `staging_workflow` et `prod_workflow` (le dépôt principal : ses MEP portent ticket et release, cron équipe), puis `github.deploys` = d'autres dépôts, `[{repo, label?, staging_workflow?, prod_workflow}]` (`label` par défaut : le nom du dépôt sans `front_`). Le cron live relit leurs runs chaque minute, en parallèle et par requête conditionnelle (ETag, `304` gratuit) ; un run du jour dont le titre contient une version est une MEP, nommée « label version » hors dépôt principal (`live_snapshot.py`). Profil equipe : les 8 autres dépôts de la revue de PR multi-dépôt.
- Tickets créés : étape `new_tickets` du cron équipe (JQL `created >= <dernier daily>`, auteur compris), mise en forme par `team_shape.py` (`team.new_tickets` : key, summary, type, status, cat, created, by, by_name). La page ne garde que les auteurs de l'équipe (`teamCreated`, par compte Jira ou par nom) : stand-up de la facilitatrice depuis `prevDaily`, fil du jour (« X crée »), pile de feuilles sur son caisson depuis `lastDaily` (`rolePile`).
- Changements de statut (âge dans le statut `since`, passages de colonne du jour) : étapes `team_keys` (clés du sprint en cours) puis `status_log` du cron équipe, `POST /rest/api/3/changelog/bulkfetch` filtré sur `status`. `team_shape.py` les rattache aux tickets de `jira_team` par id, au format de `expand=changelog`. Jamais `expand=changelog` sur `jira_team` ni `jira_closed` : il ramène chaque version de la description (12 Mo par run, 80 runs par jour). Pièges : bulkfetch date en millisecondes epoch (converties en ISO), et Kronn ne sait pas paginer son `nextPageToken` (dans le corps) : une seule page de 1000 changements (353 pour 57 tickets en octobre 2026).
- Étiquettes des agents (`41-people.js`) : icône (`agents[].icon`, sinon devinée du rôle par `AGENT_ICONS`) et métier court (`agents[].short`, sinon le rôle avant son premier « — », sans « Cron » ni cadence, 24 caractères). Réglage `ui.agent_label` : `both` (défaut, « 🔎 Dwight · Reviewer de PR »), `office` (prénom seul) ou `metier` (défaut du mode TV). Piles des bureaux (`40-furniture.js`) : barres de tickets `pileOf` de son côté de la table, caisson côté allée `rolePile` (`roleItems` : feuilles `sm`, dossiers `qa`, 6 dessinés + pastille du nombre) ; zones survolables `PILE_HITS` (remises à zéro à chaque image), infobulle `pileTip` (80-input.js). Paramètres d'affichage : Kronn transmet ceux de l'adresse `#page/<id>?tv=1&scene=standup` dans `KronnPageData.page.params` (onglet autonome seulement) ; `applyViewParams` (75-tv.js) les applique une fois, au démarrage ou au premier `kronn:page-data` qui en a, sans écrire le réglage mémorisé (`setTv(on,false)`). Passions (`38-passions.js`, roster `passion`) : `passionSlot` (un créneau par jour ouvré, rng clé × jour, fenêtre `PASSION_WINDOW`), `passionMoment` (état `passion`, zone `visit` = `besideSeat`, après `teamScene`), `holoEvening` (`soir_holo`, avant le test des heures de bureau), `drawPassion` (après le sprite) ; cartes `passionCards` (GitFut : dataset `gitfut` de l'étape `gitfut` du cron fiche de paie, fond retiré dans le navigateur par `gitfutCutout`). Écran du boss (`47-bosspages.js`) : dataset `bosspages` {generated_at, pages[{id, title, updated, img}]} publié par l'étape `pages` du cron fiche de paie (`workflows/pages_snapshot.py` : HTML + datasets de chaque page dans un fichier local avec `window.KronnPageData`, capture Chrome headless 1280×800, réduite en JPEG 320×200 par `jpeg()` de `_lib.py` (Pillow, au besoin celui du venv du dépôt, sinon `sips`), cache `~/.cache/kronn-bureau/thumbs/` par révision du HTML et des données, sortie bornée sous 90 Ko) ; `drawBossPages` remplace l'écran du bureau du boss (`bossScreenRect`, zone `bosspages` de `hitZone`), `openBossPages` la fenêtre de cartes (Échap ou fond pour fermer ; liens en `index.html#page/<id>` : Kronn ouvre dans l'onglet courant un lien vers sa propre adresse, et dans un nouvel onglet un chemin différent). Noms sur le plan : `nameShown(c)` ; en mode TV, un agent n'a son étiquette que dans un état de `AGENT_BUSY` (work, srv, meet, gate), survolé ou sélectionné.
- Scènes d'équipe (`37-scenes.js`, `teamScene`) : événements `move` du jour (`team.events`) vers les statuts de `jira.flow` (`jira_flow` dans la config de la page, défauts `assemble.JIRA_FLOW`). Réouvert : avec un invité `on: "reopen"` (le héraut, ex. Gandalf chez equipe, sprite `teams/equipe/sprites/mage`, composé des calques LPC), face-à-face de 3 min en salle de réunion (places `meet` : l'assigné d'un côté de la table, l'auteur et le héraut en face, bulle du héraut agrandie ; places `gate` à défaut, `heraldScene`), puis le héraut repart ; sans héraut, l'auteur va voir l'assigné 2 min. Mise en prod réussie : avec un invité `on: "prod"` (Yoda chez equipe, sprite `teams/equipe/sprites/yoda` ; « le sage » dans la démo, recette à peau `#rrggbb`), `prodHeraldState` : 3 min en zone `stage` à côté de l'auteur (zone `daily` si la prod finit pendant le daily, `stageout` si le plateau est fermé), réplique `shout` agrandie (`{name}` = prénom de l'auteur, retiré avec sa virgule s'il est inconnu), puis départ. Les bulles dessinées sont notées dans `BUBBLE_BOXES` (41-people.js) : une bulle `big` prend la position qui en recouvre le moins (centrée, à droite, à gauche, puis surélevée avec une tige). À tester : l'assigné porte le dossier au testeur (`deliver`), pile de dossiers sur le caisson du testeur (`rolePile`). Validé : pouce du testeur (`thumbs`), bras levés de l'assigné (`cheer`). Sprint : `kickoff` devant le Kanban 5 min après le daily du premier jour, `pizza` de 12h à 12h40 le dernier jour (boîtes sur la table de la cuisine, `sceneFurniture`). Priorité : après le daily et la MEP ; pour le boss, après ses validations.
- Tickets à estimer au sprint planning : étapes `future_sprints` (sprints futurs du board, dans son ordre), `planning_jql` (`planning_jql.py` : JQL des 2 premiers, champs de points vides via `cf[id] is EMPTY`, hors statuts terminés) et `planning_tickets` du cron équipe ; `team_shape.py` publie `team.planning` = `{sprints:[{id, name, start, end}], tickets:[{key, summary, type, status, cat, sprint, who}]}` (null sans Jira), lu par `scenePlanEstimate` (`76-tvscenes.js`).
- Cérémonies (`ceremonyAt`, `ceremonyHost` dans `30-data.js`) : `rhythm.planning` (vendredi 10h, 30 min, facilitatrice) et `rhythm.retro` (jeudi 15h, 60 min, `every: 2` depuis `from: "2026-10-15"`, animateur tiré au sort d'après la date, hors intérimaires). Sur le plan, `ceremonyState` (`37-scenes.js`) : animateur en bout de table (`headSpot`, place `meet` tournée de côté), les autres en zone `meet` ; priorité après le daily et la MEP, pour le boss après la fête de MEP. En TV (`76-tvscenes.js`), `sceneMode` = `daily`, `planning`, `retro` ou rien ; `planningScenes`, `retroScenes`, `toggleScenes`, touches S, P, R. Tests : `tests/ceremonies.test.js`.
- Invités de passage : les communs (`team/guests.json` : les hérauts Gandalf et Yoda, planches dans `sprites/common/`, assemblées dans `sprites/common.json` par `build_sprites.py` ; `common_guests: false` dans la config pour les retirer), puis la clé `guests` du roster du profil, puis de la config (`guests()` dans `assemble.py`, embarqués avec le roster ; même clé : le dernier remplace). Chacun : `key`, `name`, `sprite` (sprite fourni) ou une recette dans `cast.json`, `role`, `stay` ([min, max] en minutes, défaut [20, 40]), `chance` (de passer, défaut 1), `at` (« HH:MM », heure fixe, avec `jitter` minutes de flottement), `days` (`all` = aussi le week-end), `tour` (le tour des salles dans l'ordre de `GUEST_TOUR` au lieu de saluer les collègues), `shout` (sa bulle). Au plus une visite par jour ouvré, à une heure tirée au sort pour la date (la même pour tous), entre une heure après l'ouverture et une heure avant la fermeture (`rhythm.office_hours`) ; toutes les 3 min il change d'endroit : un collègue à son bureau ou un coin du bureau (`guestState`, `35-state.js`). Jamais un collègue (`person` ignoré) : hors équipe, Qui fait quoi, compteurs et fil. Exemples : le tour de minuit de Hank et les hérauts Gandalf et Yoda (`teams/equipe/`), David Wallace dans la démo. Un sprite fourni peut n'être qu'une planche de marche (`*walk*.png`) : `build_sprites.py` en tire la pose d'attente.
- Le canard (`39-duck.js`) : `duckAt(t)` = position, fonction pure du temps (rng `keySeed('duck')` × jour depuis `parisMidnight`) : segments « marche vers une case tirée au sort (`walkable`, hors `seatTiles`) par `findPath`, une case par `DUCK_STEP` (1,4 s), puis pause de 20 à 60 s », prolongés au besoin et gardés pour le jour (`DUCK_DAY`, refait si le plan change) ; calculés à midi du jour (`duckWith`) pour que la fermeture du plateau ne dépende que de la date. Trié avec les personnages dans `render` (`DUCK_POS`, `drawDuck` : dessin ×`DUCK_SCALE` 1,3, flèche jaune flottante sauf quand il attend, où la bulle « ? » la remplace), zone `duck` de `hitZone` (`duckHit`, flèche comprise), ligne `duckRow` du groupe « Et aussi » du panneau (`duckStatus`, `duckRoom` = libellé du plan dans la même `light_rooms`, sinon open space ; invités `c.guest&&c.present` au-dessus, vue « Tous » seulement), fiche `renderDuck` (vue `duck` de `drawSide`). Données : dataset `gates` (`gates_snapshot.py`, chaque minute) `projects` = `[{id: "none", name: "Sans projet"}]` + `GET /projects`, `ducks` = discussions dont le titre commence par « 🦆 » (14 jours, 15 au plus, `{id, title, project, updated, awaiting}`, `awaiting` = `pending_question_count` > 0), lus par `readDuckData`. Bouton `bureau-duck` (`launchBlock`, ligne liée `{id}` → `project_id`) : workflow « Le Bureau · parler au canard » (`workflows/templates/duck.json`, clé `actions.duck`, variables `project_id` et `topic`), étape Exec `duck_start.py` : `POST /discussions` (`project_id` null pour « none », titre « 🦆 » + première ligne du sujet, 70 caractères, `ClaudeCode`, `fr`), puis `POST /discussions/{id}/run` (la création ne lance pas l'agent ; `/run` le met en file avant de répondre en flux, on n'attend que les en-têtes), sortie `{discussion_id, url}`. Ces discussions ne sont jamais des visiteurs (`is_bureau_disc` de `_lib.py`, `bureauDisc` de `30-data.js`).
- La page en reçoit une partie (`page_config()` dans `assemble.py`) ; les scripts la reçoivent injectée au rendu. Un id d'action vide retire le bouton.
- Chaque source est facultative : sans Jira ni GitHub, les blocs concernés sont masqués.

## Modifier puis publier

```sh
python3 -m venv .venv && .venv/bin/pip install pillow websocket-client   # une fois
sh tools/test.sh --chrome              # tests + page assemblée chargée dans Chrome headless
python3 tools/publish.py page          # ou workflows, ou all
python3 tools/templates.py check       # les workflows du Kronn = le rendu des modèles
```

- On édite `page/src/*` et `page/office_template.html`, jamais `dist/`. Pas d'`import` ni de ressource externe : la sandbox des pages n'accepte que du inline (images en `data:`), HTML de moins de 1 Mo.
- Un nouveau fichier `page/src/NN-nom.js` est pris à sa place dans l'ordre.
- Captures de la documentation : `.venv/bin/python tools/shots.py [nom...]` (page de démo, dans `docs/img/`).

## Ajouter un thème

Un thème d'interface = un fichier `page/src/theme-<id>.css` qui ne contient que des couleurs. L'habillage pixel (cadres crénelés, boutons en relief, barres de titre, police pixel, mode TV et son bandeau « EN DIRECT ») est commun à tous les thèmes : `page/src/pixel.css`, assemblé après `styles.css` et avant les thèmes. L'assemblage prend le thème tout seul et le bouton 🎨 le propose : rien d'autre à brancher.

1. Copier `page/src/theme-classique.css` (sombre) ou `page/src/theme-equipe.css` (clair) en `page/src/theme-<id>.css` (`<id>` en minuscules, sans espace).
2. Première ligne : `/* @nom: Nom affiché */` (le nom du bouton 🎨).
3. Remplacer partout `data-skin="classique"` (ou `equipe`) par `data-skin="<id>"`.
4. Changer les couleurs du bloc `:root[data-skin="<id>"]` :
   - fonds `--bg`, `--panel`, `--chip` ; textes `--ink`, `--muted`, `--accent`, `--ok`, `--warn`, `--err` ; `color-scheme` (light ou dark) ;
   - habillage pixel : `--line` (cadres et barres de titre) et `--on-line` (leur texte), `--line-hover`, `--brand` (aplat de la marque) avec `--on-brand`, `--brand-lo`, `--brand-hi` (relief du bouton actif), `--bevel` (relief des boutons), `--drop` (ombre décalée), `--btn-hover`, `--sel-bg` (carte sélectionnée), `--h1-shadow`, `--appr-ink` et `--appr-bg` (badge apprenti), `--on-warn` et `--on-err` (texte des pastilles), `--select-arrow` (flèche des sélecteurs, une image SVG en `url(data:…)` de la couleur du texte).

   Mode TV (facultatif) : un bloc `:root[data-skin="<id>"] body.tv` qui redéfinit les variables `--tv-*` de `styles.css` (fond, barres, cartes, traits, textes, états, `--tv-btn-bevel`) ; sans lui, l'écran mural garde les couleurs sombres du Classique.
5. `sh tools/test.sh` : `tests/test_theme.py` vérifie le nom, les variables et les contrastes (texte au moins 4,5:1 sur chaque fond, texte des aplats `--on-<aplat>` au moins 4,5:1 sur `--line`, `--err`, `--warn`, `--brand`, et de même pour le bloc du mode TV s'il existe). Un thème illisible ne passe pas.
6. Ajouter une capture : une entrée `theme-<id>` dans `SHOTS` de `tools/shots.py` (copier `theme-equipe`), `.venv/bin/python tools/shots.py theme-<id>`, puis une ligne dans `docs/fonctionnalites/13-theme-page.md`.

Une police : un `.woff2` (sous-ensemble latin) dans `page/fonts/` avec sa licence, déclarée par `@font-face{...src:url(data:font/woff2;base64,@@font:page/fonts/<fichier>.woff2@@)...}` (intégrée en base64 à l'assemblage : la sandbox des pages n'accepte que `font-src data:`). Pour être facile à lire, la réserver aux éléments courts (titre, horloge, chiffres), à la taille où elle est nette. Pour qu'un thème soit le défaut d'une équipe : `"ui": {"skin": "<id>"}` dans `teams/<équipe>/defaults.json`.

## Modèles de workflows

`workflows/templates/*.json` sont la source des 10 workflows et des 2 Quick Prompts : `publish.py workflows` pousse leur rendu dans les ids (et crée un workflow du Bureau ajouté depuis l'installation, son id rangé dans la config) de la config, en gardant les ids des étapes.

- Emplacements remplacés au rendu : `@@page_id@@`, `@@kronn.project_id@@`, `@@jira.*@@`, `@@owner_name@@`, `@@script:workflows/x.py@@`. Les variables Kronn (`{{steps.x}}`) restent intactes : jamais de `{{` ni de `@@` dans un script.
- Une étape `"_requires": "jira"` disparaît sans connexion Jira.
- `templates.py export` régénère les modèles après une modification faite dans l'interface de Kronn.
- Toute sortie d'étape Exec reste sous 100 Ko (limite de Kronn) : les scripts raccourcissent leurs listes au besoin.

## Installateur

Questions : Kronn, ton équipe (une équipe neuve par défaut, ou un profil de `teams/` : un profil qui nomme une organisation GitHub n'est installable que par ses membres actifs, vérifié avec `gh api user/memberships/orgs/<org>`, droit `read:org`), qui tu es (le champ `github` du roster propose la bonne personne ; « quelqu'un d'autre » reste dans ta config), le plan du bureau (un de `layouts/` ou ton propre fichier, refusé s'il ne passe pas `plan.py check` ; écrit dans la clé `layout` de la config), projet, Jira (testé à travers Kronn ; les colonnes du board sont lues pour proposer le classement des statuts, `jira.statuses`, `jira.flow` et `done_status`, d'après le nom de chaque colonne, sinon la catégorie Jira de son statut), GitHub (dépôt, workflows de déploiement en staging et en prod parmi ceux du dépôt, autres dépôts dont suivre les mises en prod : `github.deploys`, un nouveau dépôt reprend les workflows du principal), agent IA, tes agents (un personnage par workflow actif, placé par le plan), avatar, musique. Il crée la page et ses 9 datasets (et ajoute ceux qui manquent à une page existante), les workflows et le Quick Prompt, écrit la config, publie et lance un premier rafraîchissement. Relançable sans doublon.

- Réutiliser plutôt que créer (question `reuse`) : homonymes orphelins repris, ou id donné élément par élément, mis à jour ou gardé tel quel (`own`). Un workflow qui sert une autre page encore présente n'est jamais repris d'office.
- `uninstall.py` ne touche ni aux éléments `own`, ni aux connexions, ni aux autres workflows, et refuse une installation marquée `"protect": true` dans sa config (gardé par l'installateur).

## Plan du bureau (`layouts/*.json`)

Le plan n'est plus codé en dur : `10-world.js` construit grille, sols, portes, sièges, places et cases bloquées depuis le plan embarqué par `assemble.py` (marqueur `__LAYOUT__` ; `layout` dans `bureau.config.json`, sinon celui du profil d'équipe, sinon `layouts/open-space.json`).

- `tiles` : le sol en texte, une chaîne par rangée, un caractère par case ; `legend` dit ce que vaut chaque caractère (`#` mur, `=` vitre, `.` moquette, `c` carrelage, `s` serveurs, `r` réunion, `p` plateau, `w` toilettes, `b` parquet, `E` paillasson).
- `doors` (seuils dessinés), `exit`, `closable` (porte du plateau fermée le vendredi et le week-end), `islands` (colonnes des tables et rangs des sièges), `boss` (place et bureau), `plants`, `windows`, `blocked` (facultatif : cases bloquées en plus des meubles).
- `furniture` : meubles du catalogue (`boss_desk`, `meeting_table`, `server_rack`, `counter`, `fridge`, `kitchen_table`, `sofa`, `water_cooler`, `copier`, `toilets`, `stage_closure`), chacun posé par `at` ; il bloque son emprise (`FURN_TYPES` de `40-furniture.js`, `FURNITURE` de `tools/plan.py`, tenus identiques par un test).
- `wall` (décor mural : `whiteboard`, `mirror`, `sign` avec `text`), `clock`, `labels` (noms des pièces, position en cases).
- `spots` : places de chaque zone (`[x, y, orientation]`) ; `free_seats` : places des intérimaires ; `light_rooms` : pièces éclairées la nuit ; `objects` : rectangles cliquables (TV, Kanban, planning, paie, employé du sprint).
- `seating` : qui s'assoit où, par numéro de siège (`{"I2.R2": "p_pam"}` = îlot 2, côté droit, rang 2). Le plan est maître : la place `seat` du roster ou d'un agent (`"I2.R2"` ou l'ancien `[x, y]`) ne sert que s'il ne place pas la personne. Les autres reçoivent un siège libre, toujours le même tant que le plan ne change pas : collègues, puis agents, puis intérimaires (`free_seats` d'abord). La place du boss revient aux intérimaires.
- Vérifier un plan, voir ses sièges, son rendu :
  ```sh
  python3 tools/plan.py check [plan.json] [--json]   # erreurs bloquantes et avertissements, avec les coordonnées
  python3 tools/plan.py seats [plan.json]            # sièges numérotés, qui s'y assoit, et qui change de place par rapport au plan actuel
  .venv/bin/python tools/plan.py preview [plan.json] # capture du plan dans dist/plan.png
  python3 tools/plan.py share plan.json              # le proposer à toute l'équipe (share defaut : retour au plan embarqué)
  python3 tools/plan.py from-image croquis.jpg       # brouillon depuis un croquis ou une photo (CLI claude), vérifié et corrigé
  ```
  Le vérificateur contrôle la forme (taille, rangées, légende, murs du bord et du fond), la sortie et les portes, les meubles et sièges sur du sol, l'accès depuis la sortie à chaque siège (par son allée) et à chaque place, les zones dont la machine à états a besoin, les places libres, les objets cliquables. `publish.py page` refuse un plan invalide.
- Plan d'équipe partagé : `plan.py share` lance le workflow « Le Bureau · plan » (`layout_save.py` revérifie avec les règles de `_plan.py`, une gate attend le boss, puis `PublishPageData` remplace le dataset `layout` : `{updated_at, layout}`, `layout` null = plan embarqué). La page le lit au démarrage (`readLayout`, 00-config) et à chaque rafraîchissement : `applyLayout` refait monde, toile, fond, meubles, lumières (`buildWorld`, `sizeCanvas`, `buildFurniture`, `buildBg`, `bakeFurniture`, `buildRooms`) et téléporte chacun à sa place. Sans dataset lisible, le plan embarqué reste.
- Brouillon depuis une image : `tools/plan_prompt.md` décrit le format et les règles au modèle ; c'est aussi le début du Quick Prompt « Le Bureau · plan vers brouillon » (`workflows/templates/sketch.json`, emplacements `@@text:tools/plan_prompt.md@@` et `@@root@@` = dossier du dépôt, pour les commandes). `plan.py from-image` lance `claude -p` (outil Read seul, `--resume` d'un tour à l'autre) : un brouillon, puis jusqu'à trois corrections avec les erreurs de `validate`. La clé `_notes` (suppositions) est affichée puis retirée ; `{"_error": …}` = pas un plan. `BUREAU_CLAUDE` remplace le CLI (tests : un faux `claude`). Le Quick Prompt n'a pas de variable : seul un QP sans variable s'enchaîne dans une discussion, après l'image jointe. Exemple : `docs/img/croquis.png` → `docs/exemples/plan-croquis.json`.
- Obligatoires pour la page : `boss` (`seat`, `desk`), `spots`, `objects`, `islands`. Les listes `closable`, `plants`, `windows`, `furniture`, `light_rooms`, `wall`, `labels`, `free_seats` sont facultatives (la page s'en passe, test dans `tests/layout.test.js`).
- Les seuils de porte et le bord du plateau se déduisent du plan (murs voisins, sol de plateau), plus de rangées écrites en dur.
- Zones facultatives (plateau TV, canapé, table, fontaine, copieur…) : sans elles, les personnages se replient ailleurs (`ZONE_FALLBACK` de `35-state.js`). La toile prend la taille du plan.
- Décor des thèmes saisonniers (`46-themes.js`) ancré sur le plan : ce qui décore un meuble suit ce meuble (`onF`, absent du plan = pas de décor), l'open space suit les îlots, ce qui flotte (ballons, nœuds) est placé en proportion du plan.
