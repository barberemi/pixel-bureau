# Chaîne d'implémentation d'un ticket (#76, #125)

> Modèles `workflows/templates/impl*.json`, scripts `workflows/chaine.py` (dossier, postes, Code, bilan), `workflows/chaine_controles.py` (contrôles, aiguillage, fin d'essai, retours locaux) et `workflows/chaine_pr.py` (lanceur, PR, revue, retours, publication), leur commun `workflows/_chaine.py` (recopié dans chacun au rendu, comme `_lib.py`), réglage `impl` (pack ou config). Trois scripts parce que Kronn passe chacun en un argument `python3 -c`, 128 Kio au plus sous Linux : rendus, ils restent sous 110 Kio (`templates.MAX_SCRIPT`, test) et ne reçoivent que leur part de la config (`templates.CHAINE_CFG`). Plus bas, « `chaine.py <commande>` » désigne la commande dans celui des trois qui la porte. Relevé le 2026-10-30, plusieurs dépôts et reprise le 2026-10-30.

## Forme

Un ticket avance sur une chaîne de postes. Un poste = un sous-workflow Kronn à but unique, avec son agent, son modèle et ses skills [src: file: tools/templates.py:IMPL_AGENTS].

```
impl (lanceur, 0 token)          composants Jira -> dépôts -> projets Kronn ; une chaîne par dépôt ; un passage par ticket et par dépôt ;
                                 POST /mcp/workflow-trigger avec project_id et ticket, mode, depot, soeurs, partie, reprise
└─ impl_chain (parent, 19 étapes, project_scope All, require_isolation, concurrency_limit 4)
   ticket · prepare · [cadrage = 📋 Plan] · compris · dossier · orchestrateur_plan · ✋gate_plan
   · mode · [code] · [controles] · orchestrateur · aiguillage · ✋gate_escalade
   · [livraison = 📤 PR · [revue_pr] · [retours]] · ✋gate_pr · [publication] (Stop) · commente_plan (Plan seulement, puis Stop)
   · fin_essai (Goto seulement : escalade en essai, Stop) · rattrape (Goto seulement : Code en échec)
   cadrage (📋 Plan) = entree · releve (git grep) · propose (un agent, tier reasoning) · existe (chemins) · rapport
   controles = [tests] · missions · parallele (📏 règles, 🔒 sécurité, ⚡ perf · a11y, 🎯 besoin, 📚 doc : un sous-agent chacun, en même temps) · range · bilan
   code = entree · [affecter] · plan · code (une session, un commit par lot) · verif · relecture · tri (3 essais) · bilan
```

`[x]` = sous-workflow `impl_x`. Chaque poste a de la place pour grandir : 20 étapes par workflow, comptées séparément pour chaque sous-workflow [src: url: https://github.com/DocRoms/Kronn/blob/main/backend/src/api/workflows.rs].

## Règles du moteur qui dictent la forme

- Kronn refuse un sous-workflow qui contient une gate : les trois gates sont dans le parent.
- Un sous-workflow sans projet tourne dans le projet et la copie de travail de son parent : les postes n'ont pas de `project_id` (`SHARED_WORKSPACE`), le parent a `project_scope: All` et pas de projet ; c'est le lanceur qui choisit le projet au lancement (`project_id` du trigger). Une étape `TriggerWorkflow` ne sait pas passer de projet, d'où l'Exec du lanceur qui appelle l'API.
- Le commentaire d'une gate « Changements » n'est injecté que dans le prompt d'une étape Agent. Une gate qui renvoie à un sous-workflow perdrait le commentaire : la chaîne le passe aux postes par leur variable `retours` (`{{state.last_human_feedback ?? ""}}`), le poste l'ajoute au dossier (`retours.md`, une seule fois par texte).
- Après « Changements » à une gate, Kronn coupe le run au premier passage de l'étape cible et reprend à l'étape qui SUIT, dans la définition, la dernière étape gardée : si celle-ci avait sauté par un Goto, la reprise tombe sur l'étape sautée. À l'essai d'DM-6550, un retour au Code depuis l'escalade a ainsi exécuté `commente_plan` (le plan posté dans Jira en mode essai). D'où l'ordre : le Code suit `mode` (code 0), le commentaire du plan est la dernière étape (`mode` y saute en code 4), la publication s'arrête par un Stop. Reste exposé, sans effet externe : une reprise qui a sauté au Code ou aux contrôles repartirait du poste Plan.
- `on_result` ne lit que les signaux : `exit_3`/`exit_4` d'un Exec pour brancher, `SUBWF_FAILED` pour un poste en panne.
- Le garde-fou docs de Kronn agit APRÈS une étape Agent : une doc modifiée qui ressemble à un secret (faux positif sur un contenu déjà là) fait échouer l'étape (« Document audit failed », puis `<doc>: write rejected: …`, puis « Agent result: » et l'enveloppe de l'agent) et efface son `on_result` : l'étape Agent elle-même ne peut pas brancher. Le parent, si : le `code` (SubWorkflow) a `SUBWF_FAILED` → Goto `rattrape` (dernière étape, atteinte seulement ainsi), qui lit `{{steps.code.data.last_output}}` (sortie de la dernière étape du sous-run). `chaine.py rattrape_code` : rejet du garde-fou, enveloppe de l'agent en `status: OK` et au moins un commit depuis `depart` : bilan du Code comme `bilan_code` (rapports des contrôles en `precedent_*`, `controles.json`, `quoi.json`, `missions.json`, `essais_code.json` effacés, `etape` = `controles`), `docs_rejetees` et la note « docs rejetées par le garde-fou de Kronn : <fichiers> » dans `code.json`, compteur `rattrapages`, code 4 → Goto `controles` ; sinon code 1, la chaîne échoue comme avant. Les vérifications et la relecture du Code sont sautées (les contrôles les refont) ; le poste 📚 Doc reçoit les docs refusées (`missions`), la PR aussi (`entree livraison`, ligne « doc refusée par le garde-fou » des points ouverts). Dans l'atelier, `failed_step` ignore `rattrape` et garde le Code (`Goto:rattrape`) comme cause ; un Code rattrapé est « fait ». Banc d'essai du 5 novembre : le contournement se faisait à la main.
- Un Goto compte ses passages par arête (source, cible) sur tout le run, et une étape en code non nul dont le Goto a épuisé `max_iterations` **échoue** au lieu de continuer : tous les tours (propositions, essais par lot, tests, tours de contrôle) sont comptés par le script, qui rend 0 au dernier ; `max_iterations` n'est qu'un filet.
- Une référence `{{steps.x.data_json}}` à une sortie d'agent sans enveloppe (`on_invalid: Continue`) est inconnue et Kronn refuse de rendre l'étape : toute référence à une sortie d'étape a un repli `?? …` (posé par le générateur).
- Le shadow de Kronn ne rejoue pas un workflow à variables : l'instantané chiffré des variables est rangé sous l'id du run normal, le run shadow s'arrête sur « snapshot unavailable ». D'où le mode **essai** : toute la chaîne sans push, sans PR, sans Jira (revue de la PR et retours en local, voir plus bas ; le script saute le reste, `reviewers` sort en 5 pour sauter le commentaire Jira, l'`entree` du Code sort en 5 pour sauter l'étape `affecter`).

## 📋 Le poste Plan et ta gate du plan

Avant le code, un seul poste : `impl_cadrage` (clé et id gardés pour les installations ; nom « 📋 plan »). Il fait seul ce que faisaient cadrage, schéma d'impact et patterns (essai d'DM-7851 : 7 sessions d'agent avant le code, chacune relisant le dépôt) : une étape Agent en `tier: reasoning`, sans critique, précédée de `releve` (fichiers qui citent les mots du ticket, `git grep`, et carte du dépôt) et suivie d'`existe` (chemins cités qui n'existent pas, sauf `creer`). Son rapport `cadrage.json` porte tout : `comprehension`, `inclus`, `exclus`, `criteres_acceptation`, `questions` (avec `hypothese`), `fichiers` (`modifier`, `creer`, `supprimer`, `lire`), `modules`, `donnees`, `mermaid`, `zones_risque`, `choix` et `a_eviter` (façons de faire du dépôt), `concerne`, et, sous `critique`, la sortie d'`existe` (`absents`). L'orchestrateur le reçoit par `dossier`, le Code et les contrôles par leur `entree`, le bilan y lit le schéma d'impact.

Puis une seule gate, `gate_plan`, à chaque ticket : en tête « ✋ Ce que j'ai compris » (étape `compris`, 0 token : compréhension, inclus et exclus, critères, questions à trancher avec leur hypothèse, chemins introuvables, dépôt qui semble hors périmètre), puis le plan de l'orchestrateur (`apercu`, contrôles prévus). « Changements » renvoie au poste Plan avec ton message (`retours.md` garde tout l'échange, son rapport précédent lui est redonné pour qu'il le corrige), puis l'orchestrateur refait le plan ; autant de tours que tu veux. La gate tient lieu de critique : plus de boucle propose / critique. `compris` est une étape à part (une étape de plus) : le texte d'une gate ne peut venir que d'une sortie d'étape, une Exec n'a que `stdout` et `stderr`, et le `stdout` de `dossier` porte déjà tout le dossier pour l'orchestrateur. `impl.gate_cadrage` n'a plus d'effet (la gate s'ouvre toujours). Essai d'DM-6550 : le cadrage avait compris « le front envoie des données, le mobile affiche » pour une page rendue en HTML par le front, et la chaîne a filé jusqu'au code.

Les modèles `impl_schema`, `impl_patterns` et `impl_revue` ne sont plus rendus ni installés ; leurs workflows restent dans Kronn (à supprimer à la main) et leurs ids dans `models` : la page « Chaîne · bilan » compte encore les jetons de leurs runs d'avant (`chaine_bilan.ANCIENS`), l'atelier ramène un run d'avant qui y est encore au poste voisin (Plan, ou Besoin pour la revue croisée).

## Un ticket, plusieurs dépôts : un bureau et une PR par dépôt

Un ticket Jira à plusieurs composants touche plusieurs dépôts. Kronn ne donne qu'une copie de travail par run : le lanceur pose **une chaîne par dépôt** (méthode A), chacune dans le projet Kronn de son dépôt, sur son bureau de l'atelier.

- `repos_for` : un dépôt par composant (`impl.components`, sinon un dépôt réglé du même nom, sinon `owner/composant`), sans doublon. Le champ « Dépôt » du lanceur (owner/dépôt ou nom de composant) force un seul bureau. Un dépôt sans projet Kronn : le lanceur cherche sa copie locale (origine GitHub) dans le dossier des clones (`impl.clones`, `~/Sites` par défaut), la clone là avec `impl.auto_projet` (`gh repo clone`), puis l'ajoute à Kronn (`POST /projects/add-folder`, l'origine est relevée par Kronn) ; à défaut, il est signalé dans la sortie du lanceur et les autres partent quand même.
- Garde-fou : un passage par ticket **et par dépôt**, lu dans la sortie `prepare` des runs actifs (« <ticket> sur <dépôt> »). Un run actif pas encore préparé bloque le lancement (on ne sait pas encore ce qu'il porte).
- Périmètre : la chaîne reçoit `depot` et `soeurs` ; `prepare` refuse une copie de travail d'un autre dépôt et range les sœurs dans `etat.json`. Chaque poste (et l'orchestrateur, par le dossier) reçoit une section « Périmètre de ce bureau » : ne traiter que la part du dépôt, noter ce qui revient aux autres et ce qui en dépend.
- PR sœurs : un bloc « PR sœurs » (`<!-- bureau-soeurs -->`) dans la description de chaque PR liste les autres dépôts et leur PR (ou « pas encore ouverte », branche `kronn/<ticket>`) ; la PR qui s'ouvre après réécrit ce bloc dans celles déjà ouvertes, chacune finit par lister toutes les autres.
- Plan seulement : le commentaire Jira commence par `h3. Partie <dépôt> (i sur n)` (variable `partie`, vide pour un seul dépôt).
- Contrat entre bureaux (essai d'DM-7901 : Tools écrivait `reporting_email`, le site lisait `article_report_email`) : le Plan, le Code et la PR reçoivent `contrat_soeurs()`, le plan validé de chaque sœur (lu dans son cache, `plan.json`) et où lire ce qu'elle a déjà écrit (sa copie locale, branche `kronn/<ticket>`), avec la consigne de garder les mêmes noms des deux côtés ou de les fixer dans le rapport (« Contrat partagé »). Pas de verrou : deux Code en même temps peuvent encore diverger, la revue locale et la conformité le voient.
- Limites assumées : une gate du plan par bureau ; aucun ordre de sortie entre dépôts (la relecture et la mise en prod ensemble se gèrent à la main).

## Reprise après une panne

Kronn ne reprend qu'un run interrompu (redémarrage), pas un run en échec, et supprime la copie de travail d'un run fini ou en échec ; les commits restent sur la branche `kronn/<ticket>`. La chaîne se reprend donc elle-même, sans rien changer à Kronn :

- Après chaque étape Exec, le dossier est recopié dans `~/.cache/pixel-bureau/chaine/<ticket>/<owner__dépôt>/courant/`. `etat.json` porte l'étape atteinte (`etape`) : `cadrage`, `code` (plan validé), `controles`, `orchestrateur`, `escalade`, `livraison`, `relecture`, `publication`, `fini`.
- Le lanceur a une variable `reprise` : `auto` (défaut) reprend si le dernier run de ce ticket sur ce dépôt est en échec (pas s'il a été rejeté à une gate : Kronn le finit aussi en `Failed`, sa dernière étape est alors la gate), `oui` reprend quoi qu'il arrive (par exemple un « plan seulement » relancé en complet repart au Code sans refaire le plan), `non` repart de zéro (et efface le dossier gardé).
- En reprise, `prepare` recopie le dossier, revient sur la branche `kronn/<ticket>` (locale, sinon celle poussée) et sort en 3 (Goto `code`), 4 (Goto `controles`) ou 5 (Goto `livraison`) ; 0 avant le plan validé : le poste Plan déjà fait saute à son rapport (`entree` sort en 5), l'orchestrateur refait le plan et la gate du plan revient.
- Au Code, le plan validé et les lots déjà écrits sont gardés ; si l'orchestrateur avait renvoyé au Code, ses consignes reviennent (`consignes_reprise`). Aux contrôles, un rapport déjà rendu saute (`entree` sort en 3) : le Code efface les rapports des contrôles à chaque passage, ceux qui restent valent pour ce code. Une PR déjà ouverte et relue saute à ta relecture.
- Découper la chaîne en workflows lancés un par un a été écarté : chaque run aurait sa copie de travail, les gates ne seraient plus dans un parent commun, et le dossier devrait vivre hors de la copie de toute façon.

Dans l'atelier, un run en échec des dernières 24 h reste dans « 🧯 En panne » (poste où il s'est arrêté) jusqu'à ce qu'un run plus récent du même ticket et du même dépôt le reprenne. `atelier_snapshot.py` y ajoute la cause : `deepest` descend l'étape en échec (hors code de sortie aiguillé par un Goto : `condition_result`) jusqu'au sous-run le plus profond (sortie SubWorkflow : `child_run_id`, `child_workflow_id`, `last_output`), `cause` en tire une ligne et un `cause_type` (`garde_fou_docs` avec `docs_ok` si l'agent avait rendu `status: OK`, `delai` pour un `StoppedByGuard` Timeout, `agent`, `script`, `autre`), `url` = ce run-là (`/workflows/<wf>/runs/<run>` de l'interface Kronn). Cause d'un run fini gardée dans `~/.cache/pixel-bureau/atelier_causes.json`. Un run dont `prepare` saute (`Goto:code|controles|livraison`) a `repris_a`, ses postes d'avant à `rep`, et `reprise` (panne et cause du run d'avant du même ticket et dépôt). `jour` : chiffres du tableau « Runs du jour » (`atJourBoard`, `AT_JOUR`, mur du haut, deux fenêtres retirées d'`AT_WINDOWS`), runs de la chaîne depuis minuit par pages de 50, comptés par ticket et dépôt (`tickets`, `cours`, `sortis`, `pannes` en runs, `reprises` = runs de plus que les tickets, `tok`).

## Rejouer un ticket déjà livré (essai comparé)

La variable `base` de la chaîne (commit ou branche) fait partir la branche d'un état passé, en mode essai, pour comparer le travail de la chaîne à la PR humaine déjà livrée. Le futur ne doit pas fuiter : chaque poste et l'orchestrateur reçoivent la consigne de juger par rapport à ce commit (la base distante contient la livraison), le diff part de ce commit (`depart` dans `etat.json`), le ticket ne montre ni son statut ni les commentaires postérieurs, et sa description et son titre sont ceux du départ : l'étape `ticket` lit l'historique Jira (`expand=changelog`), `a_la_date` défait un par un, du plus récent au plus ancien, les changements de `description` et `summary` postérieurs à la date du commit `depart` (`fromString`), et `ticket.md` le dit (« tels qu'au … UTC, reconstruits depuis l'historique Jira »). Banc d'essai du 5 novembre : une description réécrite après l'ouverture de la PR humaine (décisions produit) donnait à la chaîne une info du futur. Limite : l'API v2 ne rend que les 100 derniers changements d'un ticket ; les autres champs (critères, composants, liens) restent ceux d'aujourd'hui. Reste visible : l'état actuel de GitHub (environnements, rulesets) quand un agent l'interroge.

## Conformité au besoin et description de la PR

Le poste 🎯 Besoin (mission de l'étape parallèle des contrôles, bloquant par défaut) confronte le diff aux exigences du ticket (critères d'acceptation, « Qu'est-ce qu'on va faire », « Comment on teste », retours de l'humain) : `exigences` = une ligne par exigence, `fait`, `partiel`, `non`, `autrement` ou `hors_scope` ; une exigence non faite qui revient au dépôt est bloquante. Les autres contrôles jugent la qualité du code, aucun ne vérifiait le résultat demandé.

La description de la PR suit le modèle du dépôt avec un emoji par section (🎯 De quoi on parle, 🔧 Comment j'ai réglé, 🧪 Comment on teste, ✅ Validation, 🚦 Avant / après le merge), courte, sans texte d'aide laissé. Deux blocs y sont écrits par le script, pas par l'agent : « 📋 Ce que le ticket demandait, et où ça atterrit » (le tableau du poste Besoin, à l'emplacement `<!-- bureau-exigences -->`) et « ⚠️ Points ouverts » (bloquants restés et avis des contrôles, sans doublon, `<!-- bureau-points -->`). Essai d'DM-7945 : l'orchestrateur disait « avis à reporter dans la PR », le rédacteur les a omis et annonçait « qat retiré ».

## Doc du dépôt à jour

Le plan de l'orchestrateur met déjà la doc dans un lot (« La doc fait partie du travail »), mais rien ne vérifiait qu'elle avait suivi : le poste 📚 Doc (mission de l'étape parallèle des contrôles, bloquant par défaut) le fait.

- Relevé à 0 token dans `missions` (`releve_doc`), passé au sous-agent : docs du dépôt déjà modifiées par la branche (`git diff --numstat` : lignes + et -), docs qui citent un fichier modifié, son nom ou un symbole ajouté ou retiré par le diff (`git grep -F`), fichiers modifiés qu'aucune doc ne cite. Docs relevées : `docs/`, `ai/`, tout `README*`, `AGENTS.md` et `CLAUDE.md` ; `impl.repos.<dépôt>.docs` en ajoute (ex. `guide`).
- Rapport `doc.json` : `docs` = une ligne par doc lue, `a_jour`, `a_mettre_a_jour` (ce qui est devenu faux et quoi écrire), `non_concernee` ou `manquante` (un comportement ajouté que nulle doc ne décrit, avec l'endroit où il devrait l'être) ; une doc à mettre à jour est un constat bloquant, une doc manquante l'est si on en a besoin pour se servir du changement.
- L'orchestrateur renvoie au Code avec la doc à corriger et le texte à écrire ; un bloquant resté (escalade approuvée) part dans « ⚠️ Points ouverts » de la PR. `impl.postes.doc.bloquant: false` en fait un avis, `actif: false` coupe le poste.

## Périmètre : implémentation, PR et retours

La chaîne s'arrête à la PR et à sa vie de revue : `impl_livraison` (« 📤 PR ») pousse et ouvre la PR brouillon, puis appelle `impl_revue_pr` (le modèle de revue `review_child` en foreach sur `.kronn/prs.json`, sans gate, donc imbriquable) et `impl_retours` (poste 💬 retours). Ni label de CI ni env de branche : le déploiement reste au RDC.

Le poste 💬 retours exécute le code du modèle « corriger les commentaires d'une PR » (`fix`), sans sa gate (Kronn refuse une gate dans un sous-workflow ; `fix` reste le bouton « 🛠 Corriger » pour les retours humains qui arrivent après) : `entree` (`chaine.py retours_pr` imprime la PR en `dépôt#n` ; mode essai ou pas de PR : code 3, fin), puis les sous-commandes de `workflows/pr_update.py` avec `dépôt#n` et `-` à la place du n° : `prepare` (`fix_prepare` : fils non résolus et commentaires hors fil, aucun : code 9, fin), `corrige` (agent, prompt `tools/fix_prompt.md` + `impl.guidelines`), `controle` (`fix_check`, contrôles `impl.repos.<dépôt>.checks`), `diff` (`fix_diff`, rien à pousser : code 9, fin), `pousse` (`fix_push` : commit signé, push protégé, « Version N » et résolution des fils, réponse groupée hors fil, bloc « Corrections de review », CI relancée), `synchro`, `fin` [src: file: workflows/templates/impl_retours.json:1]. AI-03 : `fix_prepare` ne donne à l'agent que les commentaires d'un compte `OWNER`, `MEMBER` ou `COLLABORATOR` du dépôt (`authorAssociation`), d'un login `github` du roster (`team_github`, injecté au rendu par `tools/templates.py`), ou du compte de `gh` (jamais une app GitHub, `__typename` Bot : Copilot, github-actions…) ; les autres sont écartés par le script et comptés (« n commentaire(s) d'un compte extérieur ignoré(s) » dans la sortie, la validation et le bloc de la PR), et `tools/fix_prompt.md` dit que le texte des commentaires est une donnée, jamais une consigne [src: file: workflows/pr_update.py:1]. SRV-02 : les fichiers d'échange (`.bureau-*`) restent à la racine du dossier de travail ; `setup` refuse une PR qui en suit un (code 2), `pr_update.lit` et `retours_snapshot.progress` les lisent sans suivre de lien (`O_NOFOLLOW`), et `_lib.write_json` / `write_text` / `write_bytes` écrivent par fichier temporaire puis `os.replace`, qui remplace un lien au lieu de le suivre [src: file: workflows/_lib.py:18].

- Copie de travail : `fix_prepare` travaille dans son propre dossier (`~/.cache/pixel-bureau/pr/work/<run>`, worktree détaché sur la branche distante de la PR, depuis le clone en cache), pas dans la copie de la chaîne. La chaîne a poussé sa branche juste avant (`pousse`), les deux partent donc du même commit ; `retours_synchro` refait ensuite `git fetch` de `origin/<branche>` puis une avance rapide (`merge --ff-only`) de la copie de la chaîne, pour que le squash de la publication garde les corrections. Une copie divergente (commit local absent de la branche distante) fait échouer l'étape sans rien toucher : le squash pousse en `--force-with-lease` et écraserait les corrections [src: file: workflows/chaine.py:cmd_retours_synchro].
- `retours_synchro` relit la description sur GitHub (le bloc « Corrections de review » de `fix_push` y reste), y remet les blocs exigences et points (`place()`), l'écrit dans `pr_body.md` et la republie ; il note la passe dans `retours.json` (`passes` : run, version, fils, colonnes, poussé ; `reponses` pour `fin`), lue dans l'état du run de `pr_update.py` (`~/.cache/pixel-bureau/pr/runs/<run>.json`).
- Mode essai (banc d'essai du 5 novembre : revue et retours sautés, la seconde passe jamais mesurée) : la revue et les retours tournent en local, rien n'est posté ni poussé. `revue_prep` sort en 6 → Goto `locale` d'`impl_revue_pr` : une étape Agent (rôle `revue_pr`, `tier: reasoning`, consignes de l'équipe) relit `git diff <depart>...HEAD` comme un relecteur (ticket, description prévue `pr_body.md`, rapports des contrôles, sa revue de la passe d'avant), rend `{resume, verdict, constats}` ; `range` (`chaine.py revue_locale`) la range dans `revue_pr.json` (et `revue_pr_passe<N>.json`). Puis `retours_pr` sort en 6 avec ces constats → Goto `corrige_local` d'`impl_retours` (rôle `retours`) : corrections en commits locaux dans la copie de la chaîne ; `note_local` (`chaine.py retours_local`) compte les commits, relance les vérifications du Code pour mémoire (pas d'annulation), note la passe (`locale: true`) dans `retours.json` et `retours_pousse`. Aucun constat : code 3, fin. Ces étapes suivent `fin` (Stop sur OK) : jamais atteintes dans l'ordre, et sans modèle de revue installé le mode complet ne tombe pas dedans. Le bilan du run garde les passes (`passes_pr`) ; leurs jetons sont comptés aux postes revue PR et retours. Écart avec le vrai : la revue locale est une seule étape Agent, pas les postes de `review_child` (contexte, docs, lecture, sécurité, avis), qui lisent la PR sur GitHub.
- Seconde passe : `impl_livraison` a une étape `repasse` après `retours` (`chaine.py repasse`) ; des corrections poussées à la 1re passe : code 4, Goto `revue` (`max_iterations: 1`), la revue relit la PR (`review.py` saute une PR déjà relue au même head : le nouveau commit est relu), puis les retours ; 2 passes au plus (`MAX_PASSES`), en essai aussi (corrections locales), compteur `passes_retours` de `etat.json` remis à zéro par `pr` [src: file: workflows/templates/impl_livraison.json:1].

## Le dossier du ticket

`.kronn/chaine/` dans la copie de travail (ignoré par git), recopié dans le cache après chaque étape (reprise) : `ticket.md`, `etat.json` (dépôt, sœurs, base, branche `kronn/<ticket>`, étape atteinte, tours, PR), un rapport par poste (`<poste>.json`, dont `cadrage.json` du poste Plan ; un dossier d'avant qui a encore `schema.json` ou `patterns.json` : ignorés), `plan.json` et `lots.json`, `controles.json`, `controles_tours.json` (un instantané par tour de contrôles, pour le bilan), `retours.md`. Les postes lisent ce qu'ont écrit les précédents ; l'orchestrateur lit tout.

## Bilan et historique

Chaque run laisse un `bilan.json` dans l'historique, hors du cache de reprise (que `prepare` vide à chaque nouveau départ) : `~/.local/share/pixel-bureau/historique/<ticket>/<owner__dépôt>/<run>.json` (réglage `impl.historique`), jamais vidé. Il est réécrit par `sauve()` après **chaque** étape Exec, comme la copie du dossier : aucune étape de plus dans la chaîne (pas de Goto à replacer), et le dernier écrit vaut pour un run fini, rejeté à une gate ou en panne (Kronn ne lance aucune étape après une panne). Une erreur du bilan est écrite sur stderr et n'arrête jamais l'étape. `chaine.py bilan` l'affiche.

- Contenu : ticket, titre, dépôt, run, mode (`essai` marqué), reprise, début et dernière mise à jour, étape atteinte et issue d'après le dossier (`pr_prete`, `pr_brouillon`, `plan_seul`, `escalade`, `en_cours`), PR, version de la chaîne.
- Version : empreinte des modèles `impl*.json` et de `chaine.py`, et dernier commit qui les a touchés, calculées au rendu (`templates.impl_version`, injectées dans la config du script `chaine.py` seulement) : une modification se juge sur les tickets qui l'ont suivie.
- Tours : essais du Code (`tri_code`), tours de contrôles, escalades ; comptés dans `etat.json` (les fichiers d'essais repartent de zéro à chaque passage). `propositions` (tours propose / critique) reste vide depuis le poste Plan.
- Retours humains (`retours.md`) : la gate d'où ils viennent (poste qui les a reçus : cadrage, le poste Plan = « plan », code = escalade ou PR) et leur cause par mots-clés, 0 token : convention, découpage, périmètre, mauvaise lecture, autre. Le commentaire d'une approbation arrive aussi par `retours` : il est compté.
- Schéma d'impact (lu dans `cadrage.json`, clé `schema` du bilan gardée pour la page) : le mermaid, les fichiers prévus (créer, modifier, supprimer) contre ceux que le diff touche.
- Diff : fichiers et lignes par sorte (code, tests, doc) et le détail des docs ; rapport du poste 📚 Doc (`doc.json`) quand il existe.
- Exigences du poste 🎯 Besoin, lots du plan, résumé du cadrage et de l'orchestrateur.
- Contrôles, par poste : bloquants et avis trouvés sur tous les tours, corrigés (absents du dernier tour), restés (encore là au dernier tour : livrés en points ouverts ou tranchés à l'escalade). Un constat se reconnaît d'un tour à l'autre à son fichier et au début de son problème, chiffres ignorés.

Pas dans le dossier, donc pas dans le bilan : jetons, durées, agents et modèles par étape, attente aux gates, issue finale (panne, rejet). Ils se lisent dans l'API Kronn (runs de `impl_chain` et de leurs sous-workflows) ; un run dont aucune étape Exec n'a tourné n'a pas de bilan.

## La page « Chaîne · bilan »

Page Kronn à part (`bilan_page_id`, titre « Chaîne · bilan », dataset `bilan`), créée par `tools/install.py` avec la chaîne ; son HTML est `page/bilan.html`, autonome (ni assemblage ni démo), publié par `install.py` et `publish.py page`. La CSP de Kronn n'admet que du script en ligne : le mermaid du schéma est dessiné par la page (SVG, flowchart simple), sans bibliothèque.

Cron `chaine_bilan` (`workflows/chaine_bilan.py`, 0 token, toutes les 15 min aux heures des crons, créé seulement avec la chaîne et sa page) : les bilans de l'historique complétés par l'API Kronn. Jetons par poste : étapes d'agent du parent (`orchestrateur_plan` = plan, `orchestrateur`) et des runs de ses sous-workflows (`parent_run_id`, un poste par modèle `impl_*`, `parallele` des contrôles à part, la revue du Bureau comptée avec la revue de la PR) ; l'étape SubWorkflow du parent n'est pas comptée (pas de double compte). Jetons perdus : étapes en échec (relancées) et celles d'un run en panne. Attente : durée des étapes Gate. Issue finale : `panne`, `rejete` (dernière étape une gate refusée), `annule`, sinon celle du bilan. Un run fini n'est relu qu'une fois (`~/.cache/pixel-bureau/chaine_bilan/<run>.json`). Un run sans bilan (avant l'historique) est repris de l'API seule (`partiel`). 30 jours, 50 runs, fiches détaillées des 12 plus récents, sortie sous 90 Ko (fiches puis lignes retirées). Le champ `kpi` (jetons par ticket hors essais, écart avec la version d'avant dans le libellé) est le chiffre du vidéoprojecteur (`pages_snapshot.kpi_of`).

Non mesuré : une sortie d'agent invalide (`on_invalid: Continue`) n'est pas reconnaissable dans les runs ; ses jetons ne sont pas comptés à part.

## Allers-retours

- Avant le code : le poste Plan en une session, sans critique ; ta gate du plan (« Changements ») est la seule boucle.
- Le Code écrit tout en une session (un commit par lot, ou par sujet en correction), comme un développeur seul ; puis `verif` (commandes du dépôt) et `relecture` ; `tri` le relance tant que c'est rouge, 3 essais. L'essai d'DM-7851 écrivait lot par lot (une session, une vérification et une relecture par lot) : 5 lots, 15 sessions.
- Une vérification rouge est relancée sur une copie du point de départ (`git worktree` détaché dans le dossier) : seules les lignes d'erreur nouvelles comptent (chiffres et chemins ignorés), ce qui était déjà rouge au départ est noté `deja_la` et ne fait pas boucler le Code.
- Contrôles : 🧪 tests d'abord (le poste écrit des tests), puis règles, sécurité, perf · a11y, besoin et doc dans une seule étape Agent qui lance un sous-agent par poste, tous en même temps (Kronn ne lance pas de sous-workflows en parallèle : son `foreach` est séquentiel), `range` range leurs rapports poste par poste, puis `bilan`. La 🔁 revue croisée par une autre famille de modèle est retirée : la revue de la PR (`impl_revue_pr`) relit déjà le diff. En série, un tour prenait 45 à 50 min à l'essai d'DM-7851.
- Coût des contrôles (runs du 5 novembre : 44 $ sur 143, coordinateur et 60 sous-agents sur Opus, tours 2 et 3 : 21 $) : le coordinateur `parallele` est en tier `economy` (il lance et transmet) ; `missions` donne le modèle de chaque sous-agent (`chaine_controles.SOUS_MODELES` : sécurité sur `opus`, les autres sur `sonnet` ; `impl.postes.controles.modeles` par poste), écrit le contexte commun dans `.kronn/chaine/controles_contexte.md` (le coordinateur ne le recopie pas) ; chaque sous-agent écrit son rapport dans `.kronn/chaine/rapports/<poste>.json`, que `range` lit quand le coordinateur ne le rend pas sous sa clé. Tours 2 et suivants (`garde_rapport`) : un poste dont le rapport précédent est `ok` le garde sans sous-agent ; ceux qui ont bloqué repassent, et ceux de `impl.postes.controles.toujours` (`["securite"]` par défaut : une correction peut ouvrir une faille) ; `relance: "tous"` les relance tous [src: file: workflows/chaine_controles.py:garde_rapport].
- Tour suivant : tous les contrôles repassent (une correction peut casser autre chose), avec le diff de la correction depuis leur dernier passage (`controle_sha`) et leur rapport précédent (`precedent_<poste>.json`) ; ils relisent surtout la correction. 🎯 Besoin juge toujours l'ensemble.
- Entre les contrôles et le code : l'orchestrateur décide `livrer`, `retour_code` (consignes) ou `humain` ; `aiguillage` compte les tours (`impl.max_tours`, 3) puis passe la main à la gate d'escalade.
- Mode essai : personne ne tranche, l'escalade arrête le run au lieu d'ouvrir la gate (banc d'essai du 5 novembre : la gate d'DM-7238 approuvée sans regarder, sortie avec 3 bloquants Doc). `aiguillage` sort en 6 → Goto `fin_essai` (`chaine.py fin_essai`) : refus explicite, « escalade en essai : bloquants restants N (postes) » et la liste, `note_fin` et `refus` dans `etat.json` puis le bilan (issue `escalade`), dossier gardé ; exit 0 et Stop : le run finit réussi, ni panne ni reprise automatique. En plan et en complet, rien ne change.
- Un poste bloquant (règles, sécurité, tests, besoin, doc par défaut ; `impl.postes.<poste>.bloquant`) ne s'écarte que par les réglages ; l'orchestrateur peut écarter perf d'un ticket.

## Réglage `impl`

`repos.<owner/dépôt>` : `base` (sinon `main` ; absente du dépôt distant : sa branche par défaut, ex. `master`), `checks.regles` et `checks.tests` (commandes `sh`, chaîne ou `{cmd, subdir}`, emplacements `{worktree}`, `{main}`, `{php}`, `{ts}`, `{tests_php}`, `{tests_ts}`, `{files}` ; une commande dont les fichiers visés manquent est sautée), `ci_label`, `env_label`, `env_url`, `reviewers`, `docs` (docs relevées pour le poste 📚 Doc en plus de `docs/`, `ai/`, `README*`, `AGENTS.md`, `CLAUDE.md`), `deps` (dépendances du checkout principal à rendre visibles dans la copie de travail, ex. `["application/vendor", "node_modules"]`, vide par défaut). `components.<composant>` quand un composant ne porte pas le nom de son dépôt. `postes.<rôle>` (`cadrage` pour le poste Plan, `code`, `code.relecture`, `controles`, `tests`, `doc`…) : `agent`, `tier`, `model`, `skills` en plus, `actif`, `bloquant`. `skills` et `guidelines` de l'équipe pour le code et les contrôles. `max_tours`, `max_lots`. `clones` (dossier des copies locales, `~/Sites` par défaut) et `auto_projet` (cloner un dépôt absent). `historique` : dossier des bilans de run (`~/.local/share/pixel-bureau/historique` par défaut). `references` : dépôts standard de l'équipe (celui qui fixe les conventions) que chaque bureau peut lire, comme ses dépôts sœurs, par leur copie locale (projet Kronn), jamais modifiés.

Dépendances dans la copie de travail (`deps`, banc d'essai du 5 novembre : sans `vendor/` ni `node_modules`, les agents du Code et des Tests montaient des conteneurs à la main ou commitaient sans tester) : `prepare` (nouveau départ et reprise) et la copie du point de départ des vérifications (`base_worktree`) posent un lien symbolique vers `{main}/<chemin>` quand le chemin manque, sans rien copier (`lie_deps`). Jamais commité : un motif `vendor/` du `.gitignore` ne couvre pas un lien (git le voit comme un fichier), le chemin est alors ajouté à `info/exclude` (`git rev-parse --git-path`, commun à toutes les copies du dépôt, checkout principal compris) ; s'il n'est toujours pas ignoré, le lien est retiré. Les chemins liés sont dans `etat.json` (`deps`) et le prompt du Code et des Tests dit « lance les tests directement ». Limite : les dépendances sont celles du checkout principal (verrou de sa branche, pas forcément celui de la base rejouée) et de la machine hôte : un `node_modules` installé sous macOS a des binaires natifs (esbuild, sass, swc) qui ne tournent pas dans un conteneur Linux, et le lien absolu ne se résout pas dans un conteneur qui ne monte que la copie de travail. Une commande de vérification réglée en conteneur monte donc ses dépendances elle-même (`-v {main}/…/vendor:/app/vendor:ro`, ou un `node_modules` installé dans le conteneur), comme ci-dessous.

`vendor` de Composer (`vendor_composer`, essai d'DM-7901) : un lien sur tout le dossier mettait la racine de l'autoload (`dirname(vendor)`, liens résolus) dans le checkout principal ; tous les tests PHP échouaient (« Class not found », `.env` introuvable), en conteneur comme sur la machine, et à l'étape `lance` l'échec passait pour « déjà là » au point de départ. Un `deps` qui contient `composer/autoload_real.php` devient un vrai dossier : `composer/`, `bin/` et les fichiers du haut recopiés (1,3 Mo sur un gros dépôt PHP), chaque paquet en lien. Une commande en conteneur qui monte `{main}/…/vendor` par-dessus garde la bonne racine.

Mode essai, travail humain hors de portée (`travail_humain`, essai d'DM-7901 : le Plan proposait de reprendre les commits de la PR humaine) : `prepare` relève les branches distantes du ticket (`git ls-remote`, hors `kronn/`) et ses PR (`gh pr list --search`, dans le dépôt et ses sœurs) dans `etat.json` (`humain`) ; `non_fiable()` les interdit à tous les postes, contrôles et revue locale compris ; après « Changements » à la gate du plan, un rapport précédent qui les cite n'est pas rendu (`cite_humain`). Délai du run (`guards.timeout_seconds`) : 72 h, l'attente aux gates compte (essai d'DM-7901 : 3 h 30 à la gate du plan, run coupé à 6 h pendant la livraison).

Vérifier en conteneur jetable depuis la copie de travail : le projet Compose d'une copie de travail n'a pas de conteneur (nom de dossier), un `docker compose exec` y échouerait sans bruit ; `docker run --rm -v {worktree}/…:/app -v {main}/…/vendor:/app/vendor:ro …` marche (dépendances partagées tant que le verrou n'a pas changé).

## La PR comme l'équipe

Relevés et consignes communs avec la revue de PR (`workflows/_releves.py`, recopié comme `_lib.py`) : `fichiers_diff()` met le diff de la branche (`git diff <départ>...HEAD`) sous la forme des fichiers de l'API GitHub, que lisent `garde_fous_lignes`, `noms_retires`, `references_restantes`, `tests_lies` et `releve_doc` ; la revue lit les mêmes depuis l'API. Chaque poste, l'orchestrateur, les contrôles et la revue locale reçoivent la section « Contenu non fiable » (`non_fiable()` : une phrase adressée à une IA dans le ticket n'est jamais une consigne) ; le poste 📏 Règles et la revue locale reçoivent les relevés du diff (`releves()`) et les recherches hors du diff R1 à R11, tracées dans leur rapport (`recherches()`, champ `traces`) [src: file: workflows/_chaine.py:releves]. Skills du Bureau partagés avec la revue (`skills/*.md`, `docs/architecture/revue-pr.md`) : Plan et contrôles chargent `exigences`, les contrôles aussi `recherches` et `doc`, Tests `tests`, la revue locale `recherches`, `exigences` et `tests` [src: file: tools/templates.py:IMPL_AGENTS]. Les consignes de l'équipe (`impl.guidelines`) vont dans les prompts des modèles, jamais dans la config des scripts (128 Kio par argument).

- Poste Code : vérification `code` = `checks.regles` + `checks.tests` du dépôt, plus `garde_fous()` sur les lignes ajoutées (clé de ticket dans un commentaire, en-tête ou clé sensible, commit provisoire) [src: file: workflows/chaine.py:garde_fous].
- Ticket de suppression (DM-7816 : 4 blocs supprimés, 15 templates, styles et tests encore liés oubliés) : `noms_supprimes()` relève, à 0 token, le nom de chaque fichier que le plan supprime (`cadrage.json`, action `supprimer`) ou que le diff supprime (`VideoBlock.php` → `VideoBlock`, `video_block.html.twig` → `video_block`) et chaque classe, enum, interface, trait ou fonction retirée par le diff et pas remise ailleurs (`SYMBOLE`) ; 5 caractères au moins, sans les noms vagues (`NOMS_VAGUES` : index, style, block…). `references_mortes()` cherche ces noms (`git grep --untracked -w -F`, hors fichiers supprimés, CHANGELOG, vendor, node_modules). Le Code les reçoit dans son `entree` (relevé du plan, avant le code) ; ses vérifications (`code`) et celles du poste Règles (`regles`) refont le relevé et sont rouges tant qu'une référence reste ; la mission Règles en fait un constat bloquant même hors du diff, sauf un homonyme [src: file: workflows/chaine.py:references_mortes].
- Poste Tests : contre-épreuve par mutation (garde, borne, statut), pas de mock de la règle testée, erreur d'environnement ignorée [src: file: workflows/templates/impl_tests.json:1].
- Coût du poste Tests (banc du 5 novembre, DM-7848, run `5962cea4` d'`impl_tests`) : une session `propose` de 31 min, 80,9 k jetons de sortie, 290 k écrits en cache et 65,2 M relus en cache (14,56 $) ; aux autres tickets du banc, 1 à 14 min et 0,4 à 12 M relus. Le prix vient du nombre de tours (chaque tour relit tout le contexte), pas de la taille du diff : chaque mutation coûtait une lecture, une modification, un lancement et un retour arrière, et les lancements passaient par des conteneurs montés à la main. D'où `tests_budget()` dans l'`entree` du poste : au plus `impl.postes.tests.mutations` contre-épreuves (6 par défaut), les plus importantes d'abord, les autres notées « non éprouvées » ; le fichier de test ciblé seulement, ni la suite, ni l'analyse statique, ni un build (l'étape `lance` s'en charge) ; les tests liés à chaque fichier touché donnés d'avance, par le nom (`tests_lies` : `Foo.php` → `FooTest.php`, `foo.ts` → `foo.test.ts` ou `foo.spec.ts`) ; les dépendances liées (`deps`). Un modèle plus léger n'a pas été retenu : la contre-épreuve demande de juger quelle mutation compte. À mesurer sur le prochain banc (page « Chaîne · bilan », jetons du poste tests).
